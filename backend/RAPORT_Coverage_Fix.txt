BUG-NEW-1 — NIP z separatorem kropkowym (identity.py v1.0 → v1.1)
  Symptom:  NIP formatowany jako "766-444-75.06" (OCR zamienia "-" na ".") był
            pomijany przez nowy pipeline na czystych dokumentach.
  Root cause: `_NIP_RE` używał tylko `[\-]` jako separatora.
  Fix: separator zmieniony na `[\-\.]` — NIP z kropką wykrywany poprawnie.
  Weryfikacja: Run D — doc_00002 zakrywa 766-444-75-06 (OCR odczytał jako .06).
  Status: ✅ ZAMKNIĘTY

BUG-NEW-2 — Brak warstwy numeric: KL-NNNNN / FV-* / VAT/* / UMW/* (pipeline v0.2 → v0.3)
  Symptom:  20+ encji klasy "numer klienta/faktury/umowy" pomijanych w nowym pipeline.
            Stary pipeline łapał je przez anonymizer._layer2_regex (trie + słownik biurowy).
  Root cause: Nowy pipeline nie miał odpowiednika tej warstwy.
  Fix: Nowy moduł layers/numeric.py v1.0 z wzorcami KL-, FV-/VAT/, UMW/.
       Wstawiony po apply_legal_layer w pipeline_new.py v0.3.
  Przykłady: KL-60608 → NUMER_005, UMW/2024/001 → NUMER_002.
  Status: ✅ ZAMKNIĘTY

BUG-REGRES-OSOBA — Regres OSOBA -3.7pp (Run E vs Run D)
  Symptom:  doc_00001 "Krzysztof Adamczyk" i doc_00040 "Bartosz Michalski"
            rozpoznawane w Run D, nierozpoznawane w Run E.
  Root cause: Kolejność warstw w pipeline_new.py:
              apply_address_layer (PRZED) → apply_ner_layer (PO)
              address.py v1.4 maskuje całą ulicę (np. "al. Niepodległości 161/20,
              30-001 Olsztyn" → ADRES_001). SpaCy dostaje tekst bez kontekstu
              ulicy → nie rozpoznaje OSOBA obok tokenu ADRES_001.
              W v1.2 address łapał tylko kod pocztowy ("30-001 Olsztyn") →
              ulica zostawała w tekście → SpaCy miał kontekst → OSOBA ✓.
  Fix: Pre-ekstrakcja NER przed address layer (pipeline_new.py v0.4):
       - `extract_ner_results(state, anon_map)` wywołany PO contact, PRZED address
       - SpaCy widzi tekst po PESEL/NIP/IBAN (bez wrażliwych liczb), ale PRZED
         maskowaniem adresów (kontekst ulicy zachowany)
       - Wyniki zapisane w state.ner_results (dict)
       - apply_ner_layer() używa cache jeśli state.ner_results niepusty
  Zmienione pliki:
       - pipeline_core.py: ner_results: list → dict
       - layers/ner_adapter.py v1.1: dodano extract_ner_results()
       - pipeline_new.py v0.4: extract_ner_results() między contact a address
  Weryfikacja: Run F — OSOBA R=96.3% (52/54), identycznie jak Run D.
  Status: ✅ ZAMKNIĘTY

BUG-ADDR-FP — ADRES precision 68.3% (FP=20)
  Priorytet: 🟡
  Plik: layers/address.py
  Symptom:  address.py v1.4 generuje FP z multilinii OCR. Kiedy dokument ma
            adres w dwóch liniach (np. "ul. Słoneczna 197/15\n00-001 Warszawa"),
            address layer maskuje to jako ADRES_001, ale OCR wielokrotnie
            dostarcza ten sam adres w różnych formatach (z łamaniem/bez) →
            powstaje ADRES_002 jako FP.
  Obserwacja: Run E i Run F mają identyczne FP=20 dla ADRES — pre-ekstrakcja NER
              nie wpłynęła na ten problem. ADRES precision Run D (FP=12, P=77.8%)
              była lepsza, bo address v1.2 nie łapała całego adresu.
  Uwaga: Poprawa precision ADRES wymagałaby deduplication FP multilinii bez
         rezygnacji z gains recall (93.5% vs 91.3% w Run D). Trade-off.
